# 15.2. Diseño de APIs y Servicios — Bloque 2 (ROJAS: Módulos 3 y 7)

Este documento desarrolla la especificación preliminar de **APIs y Servicios** correspondiente únicamente al **Bloque 2 (Integrante 2: ROJAS)**:
- **Módulo 3:** Gestión de Incentivos y Fidelización (`loyalty`)
- **Módulo 7:** Plataforma, Gobernanza y Administración Centralizada (`platform`, `identity`, `audit`)

Está alineado con el modelo de dominio ([`10.2`](../10/10.2/10.2.md)), las decisiones de persistencia políglota ([`11.2`](../11/11.2/11.2.md)), el modelo físico ([`12.2`](../12/12.2/12.2.md)), los aspectos AOP en NestJS ([`13.2`](../13/13.2/13.2.md)) y la arquitectura C4 Versión 3 ([`14.2`](../14/14.2/14.2.md)).

> **Especificación OpenAPI / Swagger:** [`docs/openapi.yaml`](docs/openapi.yaml) | **Visor interactivo:** [`swagger.html`](swagger.html)

## 1. Estilo y Límites de Servicio

El ecosistema adopta el estilo de **Monolito Modular sobre NestJS / Fastify (`api-service`)** (**ADR-001**), complementado por **Workers desacoplados** (`asyncJobDispatcher` con `pg-boss`) para tareas diferidas (**ADR-410**). Dentro de `api-service`, los límites entre los módulos de Rojas responden a criterios estrictos de **Contexto Delimitado (DDD)**, **Volatilidad**, **Escala/Concurrencia** y **Tolerancia a Fallos**:

| Servicio / Submódulo | Contexto Delimitado (`10.2`) | Criterios que Definen su Límite | Patrones Arquitectónicos Vinculados (`6.5`) |
| :--- | :--- | :--- | :--- |
| **Módulo 3: Fidelización y POS** (`loyaltyBackend` / submódulo `loyalty`) | `WalletPuntos`, `PerfilValidador`, `CampanaCupon`, `CuponCanjeado` | **Escala y Concurrencia:** Alta frecuencia de lectura/redención en cajas POS ($\le 1.2\text{ s}$, **AC-302**) y contabilidad estricta con `@Version` (**AC-301**). Opera tras el gateway público con **Two-Tier Fast-Gate** en Valkey para tolerar ráfagas sin saturar PostgreSQL. | *Two-Tier Fast-Gate Invalidation*, *Domain Services & Repositories*, *Observer / Transactional Outbox* (`ADR-203`, `ADR-204`). |
| **Módulo 7: Gobernanza y Plataforma** (`platformBackend` / submódulo `platform`) | `Emporio`, `User` (`ScopedRole`), `DisputaCatalogo`, `BitacoraAuditoria` | **Seguridad, Volatilidad y Aislamiento:** Tráfico administrativo de baja frecuencia pero máxima criticidad (**AC-701**, **AC-702**). Se aísla detrás de **Cloudflare Zero Trust Tunnel** (`ADR-210`), con almacenamiento *Append-Only* y exportación WORM en Cloudflare R2. | *Policy Enforcement Point (PEP) con RLS*, *Append-Only Cryptographic Ledger*, *Pub/Sub* (`RF-703`), *Template Method & Builder* (`ADR-215`). |

## 2. Endpoints Principales por Módulo (API REST / JSON)

Todos los endpoints siguen el estilo **REST** sobre HTTPS con intercambio `application/json` bajo el prefijo versionado `/api/v1`.

### 2.1. Módulo 3 — Gestión de Incentivos y Fidelización (`/api/v1/loyalty`)

| Recurso y Método HTTP | Propósito y Requisito | Esquema General de Request | Esquema General de Response |
| :--- | :--- | :--- | :--- |
| `GET /loyalty/wallets/me` | Consultar saldo de puntos del comprador acotado al emporio activo (**RF-301, RN-03**). | Header `Authorization: Bearer <jwt>`, `X-Tenant-Id: <uuid>` | `200 OK`: `{ wallet: WalletPuntos, recentTransactions: TransaccionPuntos[] }` |
| `POST /loyalty/points/credit` | Acreditar puntos tras aprobar un reporte de campo (**RF-301, AC-301**). Usa `@Version` + `OptimisticLockRetryInterceptor`. | `{ userId, puntos, referenciaReporteId }` | `201 Created`: `TransaccionPuntos` (`tipo`, `puntos`, `balancePosterior`) |
| `GET /loyalty/validators/me/reputation` | Consultar ratio de reputación y nivel de confianza (**RF-302**). | Header `Authorization`, `X-Tenant-Id` | `200 OK`: `{ reportesAprobados, reportesRechazados, ratioReputacion, nivelConfianza }` |
| `GET /loyalty/coupons/campaigns` | Listar promociones y cupones vigentes en el emporio activo (**RF-303**). | Query opcional `?standId=<uuid>` | `200 OK`: `CampanaCupon[]` |
| `POST /loyalty/coupons/redeem` | Redimir puntos para emitir un `CuponCanjeado` con código opaco `NanoID-HMAC` (**RF-303, ADR-205**). | `{ campanaId }` | `201 Created`: `CuponCanjeado` (`codigoNanoId`, `estado: "ACTIVE"`, `expiraAt`) |
| `POST /loyalty/pos/coupons/consume` | Validación y consumo atómico irrevocable en POS (**RF-304, AC-302**). Protegido por `ValkeyRateLimitGuard` y `@Auditable`. | `{ codigoNanoId, standId, ticketVentaPos }` | `200 OK`: `CuponCanjeado` (`estado: "REDEEMED"`, `redimidoAt`, `ticketVentaPos`) |

### 2.2. Módulo 7 — Gobernanza, Plataforma y Administración (`/api/v1/platform`)

| Recurso y Método HTTP | Propósito y Requisito | Esquema General de Request | Esquema General de Response |
| :--- | :--- | :--- | :--- |
| `POST /platform/tenants` | Aprovisionar nuevo emporio y `CellInfrastructure` con RLS obligatorio (**RF-705, RF-706**). | `{ slug, nombre, boundingBoxWkt, subdominio, cellType }` | `201 Created`: `Emporio` (`id`, `slug`, `estado`, `cellType`) |
| `GET /platform/tenants/{emporioId}` | Consultar configuración maestra del tenant (**RF-705**). | Path `emporioId` (UUID) | `200 OK`: `Emporio` |
| `PUT /platform/parameters` | Modificar parámetro en caliente (**RF-703, ADR-209**) e invalidar vía Valkey Pub/Sub. | `{ emporioId?, clave, valor, tipoDato }` | `200 OK`: `ParametroSistema` (`clave`, `valor`, `updatedAt`) |
| `GET /platform/disputes` | Listar disputas de catálogo del emporio (**RF-702**). | Query opcional `?estado=PENDIENTE` | `200 OK`: `DisputaCatalogo[]` |
| `PATCH /platform/disputes/{disputeId}/resolve` | Arbitrar disputa de titularidad o catálogo (**RF-702, RN-01**). | `{ decision: "APROBADA" \| "RECHAZADA", resolucionComentario }` | `200 OK`: `DisputaCatalogo` (`estado`, `resolvedAt`) |
| `POST /platform/roles/assign` | Asignar `ScopedRole` delimitado a emporio, galería o stand (**RF-701**). | `{ userId, roleType, galeriaId?, standId? }` | `201 Created`: `ScopedRole` |
| `GET /platform/audit-logs` | Consultar bitácora criptográfica inmutable del emporio (**RF-704**). | Query `?limit=50` | `200 OK`: `BitacoraAuditoria[]` (`hashActual`, `hashAnterior`, `accion`) |
| `GET /platform/audit-logs/verify` | Verificar continuidad matemática de la cadena `SHA-256` (**RF-704, AC-702**). | Header `X-Tenant-Id` | `200 OK`: `{ emporioId, entriesVerified, chainValid, verifiedAt }` |

## 3. Códigos de Estado HTTP y Formato Común de Error (Conectado a AOP)

Todas las excepciones se normalizan bajo el estándar **RFC 7807 (*Problem Details for HTTP APIs*)** y se vinculan directamente con los aspectos implementados en [`13.2`](../13/13.2/13.2.md) y [`9/9.3/aop/`](../9/9.3/aop/):

### 3.1. Formato Estándar de Error (`ErrorResponse`)

```json
{
  "type": "https://api.gamarrachain.pe/errors/optimistic-lock-conflict",
  "title": "Conflicto de Concurrencia en Billetera",
  "status": 409,
  "detail": "La billetera fue modificada concurrentemente tras agotar 3 reintentos.",
  "instance": "/api/v1/loyalty/points/credit",
  "errorCode": "LOYALTY_VERSION_CONFLICT",
  "emporioId": "11111111-1111-4111-8111-111111111101",
  "timestamp": "2026-11-25T19:30:00.000Z",
  "traceId": "trc-9f2a8c1b"
}
```

### 3.2. Matriz de Códigos HTTP y Trazabilidad con Aspectos AOP

| Código HTTP | Significado en el Bloque 2 | Aspecto / Capa que lo Emite (`13.2`) |
| :---: | :--- | :--- |
| **`200 OK` / `201 Created`** | Operación exitosa (y sellada con `AuditTrailInterceptor` cuando tiene `@Auditable`). | Controlador + `AuditTrailInterceptor` |
| **`400 Bad Request`** | Payload inválido o incumplimiento de formato en DTO (`ValidationPipe`). | Capa de Presentación NestJS |
| **`401 Unauthorized`** | Token OIDC JWT ausente/expirado o cabecera `X-Tenant-Id` faltante. | `ScopedAuthGuard` / `TenantRlsInterceptor` |
| **`403 Forbidden`** | Rol sin alcance en `ScopeContext` o ausencia de MFA en rol administrativo (**AC-701**). | `ScopedAuthGuard` (`@RequireScope`) |
| **`404 Not Found`** | Recurso inexistente o filtrado por **RLS** al pertenecer a otro emporio (**AC-704**). | PostgreSQL RLS (`TenantRlsInterceptor`) |
| **`409 Conflict`** | Colisión persistente de `@Version` en `WalletPuntos` o cupón ya reservado/consumido. | `OptimisticLockRetryInterceptor` / `FastGate` |
| **`422 Unprocessable Entity`** | Invariante de dominio violada (ej. saldo de puntos insuficiente para canje). | Servicio de Dominio (`WalletPuntos`) |
| **`429 Too Many Requests`** | Bloqueo preventivo tras 3 fallos consecutivos en login o validación POS ($< 2\text{ ms}$). | `ValkeyRateLimitGuard` |
| **`500` / `503`** | Error interno inesperado o indisponibilidad temporal de dependencias. | Filtro Global de Excepciones |

## 4. Convenciones de Autenticación, Autorización y Versionamiento

1. **Autenticación Federada (OIDC / JWT):**
   - Todo endpoint requiere `Authorization: Bearer <JWT>` emitido por **Keycloak 26** (`identity.users`).
   - Los endpoints administrativos de Módulo 7 (`PLATFORM_SUPERADMIN`, `EMPORIO_ADMIN`, `GALERIA_ADMIN`) exigen el claim `mfaVerified: true` validado por `ScopedAuthGuard` (**AC-701**).
2. **Aislamiento y Autorización con Alcance (*Scoped Roles* + RLS):**
   - La cabecera `X-Tenant-Id` (UUID del emporio activo) es obligatoria. `TenantRlsInterceptor` fija `SET LOCAL app.current_tenant` en cada transacción SQL (**AC-704**), impidiendo el acceso cruzado entre emporios.
   - `ScopedAuthGuard` verifica que el usuario posea el rol requerido (`@RequireScope`) sobre el `emporioId`, `galeriaId` o `standId` destino.
3. **Versionamiento de la API:**
   - Se adopta **URI Path Versioning** (`/api/v1/...`) para garantizar compatibilidad explícita entre múltiples clientes (`Core App Móvil`, `Web Admin SPA` y terminales `POS` aliados). Cambios disruptivos incrementarán el prefijo (`/api/v2/...`) manteniendo soporte temporal para `v1`.
